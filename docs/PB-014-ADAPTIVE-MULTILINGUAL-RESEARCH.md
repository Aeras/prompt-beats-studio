# PB-014 — Adaptive Multilingual Music Research (implementation contract)

Status: CODE_COMPLETE_RELEASE_PENDING — implementation and offline verification in Draft PR #465; production migration/publish and paid quality pilot have not occurred. Exact final HEAD/gate evidence is maintained in the PR.

## Goal

Replace the current five hard-coded English/Russian Tavily topics with a two-stage AI workflow:
**GPT-6 Luna via OpenRouter (fixed internal planner) → bounded Tavily search → creator-selected synthesis model**.
No user or Super Admin planner-model picker in V1; centralize server configuration for later changes. The planner and final synthesis are distinct billable executions with real, independently recorded usage.

## Inputs / behavior

Support artist, artist+song, and arbitrary free-form descriptions including mixed artist influences, e.g. a new rock ballad with fingerstyle guitar inspired by Scorpions and Metallica. Distinguish reference artists from the intended original song and avoid treating style references as factual claims about individual recordings. Determine likely languages of authoritative sources from the specific subject and context, never hard-code Russian or assert language solely from script/nationality. Always include English where substantively useful, but do not mandate a pointless second language. Preserve original names/script and useful aliases. If no identity can be resolved, qualify rather than fabricate.

## Coverage contract

The planner must cover eight topics across the total search plan, not necessarily one query per topic: (1) genres/influences/era; (2) instruments/performance techniques; (3) tempo/meter/groove; (4) harmony/melody; (5) vocal approach; (6) song structure/arrangement; (7) production/mix/effects; (8) source provenance/credits/interviews. Mark topics as unverified where evidence is absent. Search queries are concise, language-native and targeted, not full instructional prompts; preserve the intent and priorities of the user. Planner returns strictly validated structured JSON: request identity, referenced entities, selected source languages, bounded queries with topic tags and reasons, ambiguity markers.

## Budget and safeguards

Keep **Standard 2 Tavily basic searches** and **Extended 5 Tavily basic searches**, max three results each, unless separately justified. A Tavily search is not automatically a credit; measure provider-reported usage. Never equate topic count with search-call count. Planner invokes one small bounded GPT-6 Luna OpenRouter call per eligible job; model/provider ID MUST be verified against live installed model registry and actual provider routing before implementation; fail safely if unavailable instead of silently substituting another paid model. Execute no extra AI search/refinement calls or automatic retries on unknown outcomes. Final synthesis remains selected user model and original source/provenance checks. Keep no-sources failure and no invented facts.

## Durable execution requirements

The existing job runner currently reserves/settles one synthesis dispatch. Introducing the planner requires independent durable stages, idempotency keys, per-stage checkpoints, reservation/settlement, recorded observed/unknown provider usage and safe recovery on crash/timeout, preserving one logical user job. Never replay a possibly billed but unacknowledged dispatch. Validate owner, feature entitlement, generator model and planner availability before charges. Cost estimate must account for planner + actual Tavily usage + synthesis, with bounded call/token/time budgets (no reintroduced monetary admission cap); no double billing. No auth/RLS weakening, no unsafe dynamic URLs or source-injection execution. Any necessary SQL migration must be reviewed/replay-tested and require production approval separately. No live paid calls during automated tests.

No undocumented reasoning control is assumed. Planner alone opts into JSON-object response format through a server-only call flag; synthesis/other callers retain their prior wire behavior. The official [OpenRouter chat reference](https://openrouter.ai/docs/client-sdks/python/api-reference/chat) documents this response_format shape. The existing adapter routes explicit provider=openrouter to its fixed HTTPS chat-completions endpoint; the openai/ prefix must never route this stage directly to OpenAI.

`INSPIRATION_PLANNER` is the central server constant, mirrored by the immutable migration identity guard. A future planner identity change requires a coordinated reviewed forward migration rather than silently changing the constant. Exact installed identity, enabled/compatible flags and existing owner model permission are checked in config/admission and before every new stage dispatch, as well as SQL admission. No catalog-only fallback, alternative model, UI selector, permission expansion or automatic retry. Users without existing permission get an explicit unavailable message; their owned saved profiles remain usable. Registry access policy remains unchanged; eligible Beta testers may need an existing explicit model grant approved separately before live research.

`music-inspiration-planner.shared.ts` strictly validates echoed request identity, target/reference/intent entities and aliases, justified source languages, exactly 2/5 unique concise queries with language/topic/reason, complete eight-topic union and explicit ambiguity. Raw output is bounded to 64 KiB; query/control/length limits are enforced without truncation. Names/script are preserved. The planner requests at most 2,200 output tokens and a 20s call timeout; the existing overall Standard 90s / Extended 120s dispatch window remains. Language and topic tags are validated metadata, not independent musicological certification of query quality.

Each new job follows:

1. Service-only `start_music_inspiration_job_v3` atomically pins protocol version 2, creator-selected synthesis identity and prices, fixed planner identity/prices and a separate planner execution UUID. Duplicate request IDs preserve all original IDs/snapshots. No provider work occurs in the admission handler.
2. `claim_music_inspiration_job_v2` leases both legacy and new jobs. Planner dispatch reservation is durable and unique; the real tracked caller checkpoints raw result/observed usage before application validation. Unknown dispatch/journal outcomes stop advancement, never cause a new paid attempt.
3. Record planner usage idempotently, settle its dispatch and validate its JSON. Lease-fenced immutable plan checkpoint must precede Tavily reservation. A lost accounting/settlement/checkpoint acknowledgement reuses the raw execution receipt, not the model.
4. Execute only the persisted plan's queries, 2 or 5 basic searches, max three results each. Keep fixed-origin fetching, redirect rejection, bounded retrieval and exact receipt/quote checks. Search dispatch keys remain deterministic per job/index; observed receipts recover without another search. Actual credits come from Tavily usage, not an assumed one-credit bill.
5. Creator-selected synthesis uses the current strict research/proposal schema and canonical source metadata verification. Plan hypotheses/ambiguities are supplied as untrusted planning context, **not factual evidence**. No extra refinement model calls. Synthesis has its original independent execution identity and ledger entry even if its model happens to equal the planner model.
6. Application result persistence/profile CAS/owner RLS/PB-013 Apply remain unchanged. Observed usage/raw results survive application failure, cancellation, access revocation and recovery. Already-sent provider consumption is never assumed zero.

The job's active protocol identity is server-owned; clients cannot submit plans, planner IDs or prices. Service-only RPCs have fixed search_path and explicit ACL revocations. Existing owner SELECT RLS is preserved (including the existing owner's ability to read their own job data); no new public table, cross-user access or authenticated write is granted. Planner deletion is blocked while a job or reservation is active/unreconciled; the existing global execution-accounting guards additionally preserve unresolved financial evidence.

## Accounting and bounded recovery

Planner, Tavily and synthesis have separate durable dispatch receipts. Planner and synthesis use distinct execution UUIDs in the existing provider journal/usage/outbox, so persistence retries deduplicate per execution while genuinely distinct calls retain separate costs. Usage UI presents planner tokens/estimate/provider-reported amount independently from synthesis and search. Total estimate adds each stage once; provider-reported cost is displayed separately and never added a second time. Reasoning is already inside output, cached/write subsets use their stored tariffs, missing usage/prices remain unknown.

**No monetary caps, price-age gates or tariff changes are reintroduced.** The owner's earlier no-monetary-admission policy remains authoritative. Reservation rows fence dispatch, not reserve money from an account; legacy zero monetary reservation fields are not bills or assertions of free service. Prices are administrator-owned per-job snapshots for honest estimates, not verified invoices. Existing finite call counts, max tokens, source bounds, overall timeouts, 30-minute unstarted expiry and three recovery attempts remain. Tests exercise these limits and uncertain accounting without paid requests.

Result-only recovery gets at most 30s to reconcile/validate stored receipts and may finish an already observed synthesis after the original dispatch window. It **cannot extend any new paid dispatch deadline**. An interrupted planner can be reconciled after expiry, but new searches/synthesis then stop with a timeout rather than silently restarting research. Unknown Tavily calls without a trustworthy receipt remain unknown; they cannot be safely replayed. Provider execution exactly-once is not claimed; durable reservation prevents blind duplicate application dispatch, while network acceptance/billing can remain unknowable.
